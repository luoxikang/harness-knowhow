# PB-001: Harness 的边界应该画在哪？

## 问题

Agent 引擎（LLM 循环）和基础设施（HTTP/存储/沙盒/权限/计费）之间的分界线应该在哪？

## 关键维度

- 引擎应该知道 HTTP 吗？
- 引擎应该知道文件在哪吗？
- 引擎应该知道用户是谁吗？
- 引擎应该知道怎么计费吗？

理念：**引擎不该知道的事情越多，边界越清晰。**

## 参考方案

### 方案 A：引擎 = 子进程（Claude SDK 模式）

```
边界 = 进程边界（stdin/stdout JSONL）
引擎是 claude CLI 子进程。
基础设施（HTTP/存储/权限）都在父进程中。
```

- 边界极清晰（进程隔离）
- 但资源开销大（每 session 一个进程）
- 适合：强隔离需求，低并发

### 方案 B：引擎和基础设施全耦合（OpenCode 模式）

```
边界 = 无（同一进程）
HTTP Server、SQLite、Bash 执行全在同一进程。
通过 Plugin Hook 做有限的扩展。
```

- 开箱即用能力强
- 但引擎内部没有沙盒抽象，Bash/Read/Write 直接调 OS
- 适合：开箱即用的单实例部署

### 方案 C：引擎通过接口分离（Pi 模式）

```
边界 = ExecutionEnv 接口 + 无 HTTP
引擎只负责 LLM 循环 + 工具调度。
ExecutionEnv 接口分离沙盒。
HTTP/存储/权限/计费全在引擎外部。
```

- 边界最清晰（接口定义明确）
- 但需要自己写 HTTP 层和存储层
- 适合：长期产品，需要灵活替换沙盒实现

## 关键取舍

| | 方案 A（子进程） | 方案 B（耦合） | 方案 C（接口） |
|---|---|---|---|
| 边界清晰度 | ★★★★ | ★★ | ★★★★★ |
| 开箱即用 | ★★ | ★★★★★ | ★★ |
| 沙盒可替换 | ★ | ★ | ★★★★★ |
| 并发效率 | ★★ | ★★★★★ | ★★★★★ |
| 需要自己写 | HTTP 层 | Plugin | HTTP + 存储 |
